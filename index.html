Stage 01 · Discovery

URL discovery — how Google finds pages

There is no central registry of the web. Google must constantly discover what exists, using three main sources.

↻ Known pages

Google revisits pages it has crawled before to check for changes. Most crawling is actually re-crawling of already-known URLs.

⛓ Link extraction

When a known page links to a new URL (a category page linking to a new blog post), the crawler extracts the <a href> and queues it. This is how the crawler "spiders" outward.

🗺 Sitemaps

Site owners submit XML sitemaps (directly or via Search Console) listing URLs with <lastmod> hints, giving Google an inventory of the site.

The URL frontier

Every discovered URL lands in the URL frontier — a massive, deduplicated priority queue. It answers one question continuously: of the billions of URLs we know about, which should we fetch next? Priority is driven by how popular a URL is, how likely it is to have changed since the last visit (staleness), and how much Google wants content from that site (crawl demand).

Stage 02 · Crawling

Googlebot — the fetching machine

Googlebot is not one bot: it's a fleet of crawlers running on thousands of machines, mostly from US data centers, engineered around one rule — never take a website down.

Politeness & crawl budget

Before any fetch, Googlebot checks the site's robots.txt (cached) and respects disallow rules. Then it throttles itself per host. The amount it will crawl on your site is the crawl budget:

CRAWL CAPACITY
max parallel connections × time your server can handle — grows when the site is fast & stable, shrinks on slowdowns and 5xx errors
∧
CRAWL DEMAND
how much Google wants your URLs — perceived inventory, popularity, staleness of stored copies
=
CRAWL BUDGET
the set of URLs Google can and wants to crawl on your site
Adaptive feedback loopThe crawl rate is a live control system. Fast responses and HTTP 200s → the limit creeps up. Server errors (500), timeouts, or 429 Too Many Requests → Googlebot backs off immediately. Your server is effectively steering the crawler in real time.

Fetch mechanics

PropertyHow it works
ProtocolsHTTP/1.1 and HTTP/2 (Googlebot picks HTTP/2 when the site supports it, saving connections)
HTML limitFetches up to 2 MB per HTML page — the fetch stops exactly at the cutoff; bytes beyond it are never rendered or indexed
PDF limitUp to 64 MB; other Google crawlers default to 15 MB where unspecified
DNSHostnames are resolved through Google's own caching DNS infrastructure before fetching

Mobile-firstThe primary crawler is Googlebot Smartphone — Google predominantly crawls and indexes the mobile version of pages
VariantsSpecialized crawlers exist for images, video, news, ads, and AI training (e.g. Googlebot-Image, GoogleOther, Google-Extended)

Stage 03 · Rendering

Rendering — Google runs your JavaScript

Modern pages build much of their content with JavaScript, so raw HTML isn't enough. Google renders pages with its Web Rendering Service (WRS) — a headless, always-up-to-date ("evergreen") version of Chromium, essentially the same engine as your Chrome browser.

Fig. 3 — the two-wave processing model
Render queue

Rendering a page in a real browser is expensive at web scale, so rendering is deferred into its own queue and happens "once Google's resources allow" — from seconds to much longer.

Evergreen Chromium

WRS tracks recent Chrome releases, so modern JS features work. It loads CSS/JS/XHR like a browser (subject to robots rules on those resources) but skips things like permission prompts.

Why it matters

Content that exists only after JS runs is indexed only after Wave 2. Links must be real <a href> elements to be discovered from the rendered DOM.

Stage 04 · Indexing

Indexing — turning pages into a searchable database

Indexing is where Google works out what a page is about and whether to store it. Since the "Caffeine" rebuild, indexing is continuous and incremental — pages flow into the index within minutes-to-hours instead of waiting for periodic batch rebuilds.

Processing steps

1 · Content analysis

Parses textual content and key tags: <title>, headings, alt attributes, structured data, images and video references.

2 · Duplicate clustering

Groups pages with similar content into a cluster, then selects one canonical — the version eligible to appear in results. The rest become alternates (e.g. mobile or localized variants).

3 · Signal extraction

Collects signals about the canonical: language, country relevance, page usability, plus the link graph signals (PageRank-style authority) used later at ranking time.

4 · Quality gates

Spam systems (e.g. SpamBrain-class filters) and quality thresholds run here. Low-value, thin or duplicate pages are simply not indexed — indexing is never guaranteed.

How the index itself is designed

The core data structure is an inverted index: instead of mapping pages → words, it maps every word → the list of pages containing it (with positions and weights). That flip is what makes searching billions of documents in ~half a second possible.

Stage 05 · Serving

Serving — answering a query in ~½ second

When you search, Google doesn't search the live web — it searches the index. The serving stack retrieves candidate pages and ranks them with hundreds of signals.

Query understanding

Spelling, synonyms and intent are resolved first (systems like BERT-era language models help interpret meaning), deciding what kind of results the query deserves.

Retrieval

The query fans out across index shards in parallel; posting lists are intersected to find every candidate document.

Ranking

Hundreds of factors score each candidate: relevance, quality/authority from the link graph, freshness, page experience, plus the user's location, language and device.

Assembly

The results page is composed per query type — local packs for "bicycle repair shop", image blocks for "modern bicycle", plus features like snippets. Ranking is programmatic; placement can't be bought.

Design principles

Why it's designed this way

PrincipleWhat it means in the design
Distributed everythingNo single machine could hold the web. Crawling, rendering, indexing and serving are each spread over thousands of servers in many data centers, with replication for fault tolerance.
Queues decouple stagesCrawl queue, render queue and indexing pipeline run independently — a slow stage never blocks the others; work just waits.
Politeness firstThe crawler treats every website's health as a hard constraint, adapting speed per host from live server feedback.
Budget everythingCompute is finite even for Google: byte limits per fetch, crawl budgets per site, deferred rendering — costs are capped at every stage.
Continuous, not batchSince Caffeine, the index updates incrementally around the clock, so fresh pages can surface within minutes.
Nothing is guaranteedEvery stage filters: quality gates decide what gets crawled, rendered, indexed and shown. This keeps the index useful rather than exhaustive.
